## 1. 引言

### 1.1 编写目的

说明系统总体架构、逻辑分层、核心组件协作关系、部署形态与质量属性，供开发、测试与运维建立统一视图。模块内部算法、表字段、接口报文等见《详细设计说明书》。

### 1.2 系统目标

在 Windows 上通过 Microsoft Office COM，将 Word / Excel / PowerPoint 等文档转为 PDF，尽量保留版式；以 HTTP 服务对外提供上传、异步转换、下载与管理能力。

### 1.3 范围与边界

| 在范围内 | 不在本架构交付范围内 |
|----------|----------------------|
| HTTP API、认证与权限、上传校验、转换队列、PDF 生成与下载 | 完整 Web 前端工程 |
| 终态归档、源文件长期保留、表行 CSV 归档与 PDF 回收 | CSV 回灌导入 API |
| 前台进程与 Windows 服务形态 | 多机分布式转换集群 |

### 1.4 技术选型

| 层级 | 选型 |
|------|------|
| 语言 / HTTP | Go 1.21+、Gin |
| 持久化 | MySQL 8.0+ 或 PostgreSQL 14+、GORM |
| Office | go-ole；默认子进程 `convert-worker` 执行 COM |
| 队列 | 内存 channel + Worker Pool |
| 认证 | 短时 JWT + 用户表长期 API Token |
| 密码 | MD5 小写 hex（`pwd_hash`） |
| 服务封装 | kardianos/service（服务名 MSOffice2PdfService） |

## 3. 逻辑架构

### 3.1 分层视图

```text
┌──────────────────────────────────────────────────────────┐
│  接入层：Gin（/health、/api/*）+ 认证/权限中间件           │
└────────────────────────────┬─────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────┐
│  业务层：User / Upload / Pdf / Cleanup 服务               │
└───────┬──────────────────┬──────────────────┬────────────┘
        ▼                  ▼                  ▼
┌───────────────┐  ┌───────────────┐  ┌───────────────┐
│ 转换子系统     │  │ 存储子系统     │  │ 数据访问       │
│ Queue+Worker  │  │ storage 路径  │  │ repo + GORM   │
│ Converter COM │  │ validate 校验 │  │ domain 实体   │
└───────────────┘  └───────────────┘  └───────────────┘
```

依赖方向：handlers → service → repo / queue / storage / validate；converter 仅由 Worker 调用，**不**在 HTTP 请求路径中同步执行 Office。

### 3.2 核心组件

| 组件 | 职责 |
|------|------|
| HTTP Server | REST API；登录签发 JWT；统一 JSON；401/403/404 |
| User 服务 | 用户 CRUD、冻结、Token 重置、登录校验 |
| Upload 服务 | 校验、落盘、入队、删除归档、待转列表 |
| Pdf 服务 | 状态查询、PDF 下载/列表、pdflog |
| 转换队列 | channel + Worker；requeue / retry 扫描 |
| Converter | subprocess（默认）或 inprocess COM；非 Windows stub |
| Cleanup 服务 | ArchiveUpload；按日迁盘；CSV 表归档与 PDF 删文件 |
| 本地存储 | upload / output / expired / trash / archive |
| 数据库 | user、upload、upload_history、pdf、pdflog 等 |

### 3.3 包结构（逻辑模块）

```text
cmd/msoffice2pdf     # 入口、CLI、convert-worker 子命令
internal/
  config / domain / repo / service
  handlers / middleware / server
  queue / converter / storage / validate
```

## 4. 关键场景与主数据流

### 4.1 角色

| 角色 | 能力概要 |
|------|----------|
| 管理员 | 用户管理、查看全部待转/PDF/历史 |
| 普通用户 | 仅本人上传、下载、删除、历史与状态 |

冻结用户（status=1）禁止一切需认证操作。

### 4.2 转换主路径

```text
客户端上传 → 校验（扩展名/魔数/结构）→ upload 落盘 + 待转行
    → 入队 queued → Worker converting
    → COM 导出 PDF → 可选水印 → 写 pdf/pdflog
    → ArchiveUpload：源文件 → expired（按日目录）
                      写 upload_history，硬删 upload 行
```

失败：标 failed → 可配置重试 → 超限同样 ArchiveUpload（expired，错误码 ERR_RETRY_LIMIT_EXCEEDED）。  
用户删除：源文件 → trash（按日目录）→ history（final_status=deleted）。

### 4.3 查询与下载

- 待转：读 `upload`；归档后详情/状态回落 `upload_history`
- 原 Office：仅待转可下载；归档后不可下原文件，仍可经 history 关联下 PDF
- 历史列表：读 `upload_history` / `pdflog`；表行 CSV 硬删后以 CSV + 盘上源文件为审计依据

### 4.4 清理与归档策略（架构约束）

| 对象 | 策略 |
|------|------|
| 源 Office（expired/trash） | **长期保留，不物理删除**；按日分目录 |
| upload 表 | 仅待转；终态立刻归档硬删 |
| upload_history / pdf(+pdflog) | 超行数阈值且超保留天数：先导 CSV，再硬删表行 |
| PDF 文件 | 随 pdf 表归档删除 output 文件 |
| 旧配置 upload_ttl / history_ttl* / pdf_ttl | 忽略；启动 WARN |

## 5. 数据与存储概要

### 5.1 逻辑数据

```text
user ──┬── upload（待转）
     ├── upload_history（终态快照；upload_id=原 upload.id）
     └── pdf ── pdflog
```

`expired_upload` 为遗留表，仅迁移读，新写入走 `upload_history`。

### 5.2 目录布局

```text
upload/{uid}/...                          # 进行中
output/{uid}/...pdf                       # PDF
expired|trash/{uid}/{yyyy}/{mm}/{dd}/...  # 源文件归档
archive/history|pdf/*.csv                 # 表行导出
config/config.yaml
```

磁盘与库表必须同步更新。

```text
┌─────────────────────────────────────────┐
│  Windows 主机                            │
│  ┌─────────────────────────────────────┐│
│  │ msoffice2pdf（前台或 Windows 服务）  ││
│  │  :port HTTP + Worker Pool           ││
│  └──────────┬──────────────┬───────────┘│
│             │              │            │
│      ┌──────▼─────┐  ┌─────▼─────┐     │
│      │ 本地目录    │  │ Office COM│     │
│      └────────────┘  └───────────┘     │
└─────────────┬───────────────────────────┘
              │
       ┌──────▼──────┐
       │ MySQL / PG  │  （可同机或独立）
       └─────────────┘
```

- 配置：`config/config.yaml`；DSN / JWT 可用环境变量覆盖
- 启动：AutoMigrate、确保存储目录、清理与扁目录迁移跑一轮
- 水平扩展：本架构按**单实例 + 可配 Worker 数**设计；多实例需另行约定文件与队列隔离（当前未做）

## 7. 质量属性与安全

| 属性 | 目标 / 手段 |
|------|-------------|
| 性能 | 单实例 10+ 并发转换；API（不含转换）目标 < 500ms |
| 可靠 | 转换超时与进程兜底；COM 默认子进程隔离；重试与终态归档 |
| 可维护 | 分层清晰；结构化日志；配置模板与运行配置键同步 |
| 兼容 | Office 2016 / 2019 / 2021 / M365 |
| 安全 | MD5 密码；JWT/API Token；上传校验；本人/管理员隔离；可选 IP 白名单；COM 无头 + TEMP 沙箱 |

## 7. 质量属性与安全

### 7.1 性能指标

| 指标 | 目标值 | 度量方式 |
|------|--------|----------|
| API 响应时间（不含转换） | P95 < 500ms | Gin 中间件记录请求耗时 |
| 单文档转换时间 | Word/Excel: < 60s；PowerPoint: < 120s | 日志记录转换耗时 |
| 并发转换数 | 单实例 ≥ 4 个并发 Worker,随机器配置 | `converter.worker_count` 配置 |
| 系统吞吐量 | ≥ 100 文档/小时（典型混合文档） | 压测统计 |
| 队列容量 | ≥ 100 个待转任务 | `converter.queue_size` 配置 |
| API 请求并发 | 支持 100 并发请求（不含转换） | 负载测试验证 |

### 7.2 可用性

| 指标 | 目标 |
|------|------|
| 服务可用性 | 99.5%（月停机 < 3.6 小时），计划维护除外 |
| 故障恢复时间（RTO） | < 5 分钟（服务重启） |
| 转换任务重试 | 自动重试最多 3 次（配置 `retry_count=2` 表示额外 2 次） |
| 进程崩溃恢复 | Windows 服务自动重启（通过 service 配置） |
| 数据持久化 | 已归档数据不因服务重启丢失（upload_history + 文件系统） |

### 7.3 安全

| 层面 | 措施 |
|------|------|
| 认证 | JWT 短时会话（48h）+ API Token 长期凭证；密码 MD5（见 ADR-002） |
| 授权 | 用户级隔离：普通用户仅访问本人数据；管理员全量访问； |
| 传输安全（生产） | 推荐 Nginx TLS 终结；可选 autotls 内置 HTTPS |
| 输入校验 | 文件扩展名 + 魔数（OLE/ZIP）+ OOXML/OLE 结构校验，防止恶意文件 |
| 进程隔离 | COM 转换默认在子进程执行（subprocess），超时强杀；TEMP 沙箱隔离 |
| IP 白名单 | `server.allow_ips` 全局中间件，支持 `*` / 单个 IP / CIDR |
| 日志安全 | 禁止输出密码、Token、完整 JWT |

### 7.4 可维护性

| 维度 | 设计 |
|------|------|
| 日志 | 结构化日志（logrus/zap），含 fileid,  追踪全链路 |
| 配置 | YAML + 环境变量覆盖，配置模板与运行配置键同步 |
| 部署 | 前台运行 + Windows 服务两种形态；优雅停止等待转换完成 |
| 监控 | `/health` 健康检查端点，可用于探针 |
| 数据迁移 | 启动时自动执行扁目录迁移和遗留表迁移，幂等设计 |

### 7.5 可扩展性

| 维度 | 当前能力 | 未来演进路径 |
|------|----------|--------------|
| 转换能力 | 单机 Worker Pool，Worker 数可配置 | 多实例需改用 Redis/RabbitMQ + 共享存储 |
| 存储 | 本地磁盘 | 可抽象 Storage 接口，支持 S3/NFS |
| 认证 | 本地用户表 | 可扩展 OAuth2/LDAP 集成 |
| API | RESTful | 可增加 WebSocket 推送转换进度 |


## 8. 技术决策记录（Architecture Decision Records）

本章记录影响架构方向的关键技术决策及其背景，便于后续演进时理解设计意图。

### 8.1 ADR-001：选择内存 Channel 而非消息队列

| 项 | 内容 |
|----|------|
| **决策** | 采用 Go 内存 Channel + Worker Pool 作为任务队列 |
| **背景** | 系统需异步处理 Office 文档转换，需一个任务队列实现生产-消费模式 |
| **备选方案** | RabbitMQ、Redis Stream、数据库轮询 |
| **决策理由** | 系统设计为单实例部署，无需分布式协调；内存队列延迟低、无外部依赖；部署复杂度最低；初期业务量（日转换 < 1000）下完全够用 |
| **代价/约束** | 服务重启时队列中任务丢失（requeue 机制可部分恢复：启动时扫描 pending/queued/converting 重新入队）；无法水平扩展多实例 |
| **演进信号** | 当单实例无法满足吞吐量，或需要高可用部署时，迁移至 Redis Stream 或 RabbitMQ |

### 8.2 ADR-002：密码存储使用 MD5 而非 bcrypt

| 项 | 内容 |
|----|------|
| **决策** | 密码哈希采用 MD5（小写 hex） |
| **背景** | 系统需用户认证，密码需安全存储 |
| **备选方案** | bcrypt、scrypt、Argon2、PBKDF2 |
| **决策理由** | **重要说明**：MD5 从密码学角度已不安全，此决策主要考虑与现有企业内部系统（OA/AD）的密码哈希格式保持兼容；系统定位为内部工具而非面向公网的核心身份系统，风险可接受 |
| **风险与缓解** | 风险：彩虹表攻击、碰撞攻击；缓解：系统通过 JWT 短时会话和 API Token 机制减少密码验证频率；建议未来版本增加加盐哈希或迁移至 bcrypt |
| **演进信号** | 当系统对外暴露或集成第三方 SSO 时，必须迁移至 bcrypt/Argon2 |

### 8.3 ADR-003：源文件永久保留不物理删除

| 项 | 内容 |
|----|------|
| **决策** | 转换完成后源 Office 文件归档至 expired/trash 目录，永不物理删除 |
| **背景** | 系统需处理已转换文档的清理策略 |
| **备选方案** | 定时删除源文件、自动清理过期文件 |
| **决策理由** | 源文件是最终审计凭证，业务要求永久保留；磁盘成本低于重新生成的合规风险；按日分目录便于长期管理 |
| **代价** | 磁盘占用持续增长；需要容量规划 |
| **演进信号** | 当磁盘容量成为瓶颈时，可增加源文件压缩存储（如 ZIP）或迁移至冷存储（如 S3 Glacier） |

### 8.4 ADR-004：UI 嵌入后端 vs 分离部署

| 项 | 内容 |
|----|------|
| **决策** | 采用 `//go:embed` 将 Web UI 打包进二进制 |
| **背景** | 系统需提供 Web 管理界面 |
| **备选方案** | 前后端完全分离部署、后端仅提供 API、UI 独立 Nginx 托管 |
| **决策理由** | 单二进制部署最简单，用户无需单独部署前端；减少运维负担；适合小型内部工具的交付模式 |
| **代价** | 前端改动需重新编译整体二进制；无法单独热更新 UI；前端迭代周期与后端发布耦合 |
| **缓解措施** | 开发阶段使用独立前端 Dev Server；若 UI 变更频繁，可切换至磁盘静态目录模式（`gin.Static`） |
| **演进信号** | 当 UI 迭代频率 > 1次/周 或需独立发布前端版本时，迁移至分离部署 |

## 9. Web UI 架构

### 9.1 UI 定位与边界
- Web UI 为 MSOffice2Pdf 的官方管理/使用界面
- 调用后端 REST API，不直接操作数据库或磁盘
- 与后端的关系：独立部署

### 9.2 技术选型
- 框架：Vue 3 + TypeScript
- UI 组件库：Element Plus
- 状态管理：Pinia 
- 构建工具：Vite
- HTTP 客户端：Axios

### 9.3 UI 功能模块
后端 API为推荐，，具体见 usage.md 和服务端实现,如有冲突，以最终服务端实现为主。

| 模块 | 对应后端 API | 角色 |
|------|-------------|------|
| 登录/登出 | /api/auth/login  | 公开 |
| 文件上传 | /api/upload  | 用户 |
| 转换状态看板 | /api/uploads + /api/pdf/:fileid/status | 用户 |
| PDF 下载 | /api/pdf/:fileid/download | 用户 |
| PDFLog 查看 | /api/pdflog/:fileid/| 用户 |
| 历史记录 | /api/history/uploads  | 用户 |
| 用户管理（管理员） | /api/admin/users/*  | 管理员 |
| 系统总览（管理员） | /api/admin/uploads + /api/admin/pdfs +pdfLog | 管理员 |

### 9.4 UI 部署方式
| 方式 | 说明 |
|------|------|
| 独立部署 | 前端静态资源由 Nginx 托管，通过代理转发 API 请求 | 

#备注：UI成熟后，再 嵌入后端 | `go:embed` 将构建后的 dist/ 嵌入 Go 二进制，Gin 托管静态文件 |

### 9.5 UI 安全约束
- JWT 存储：HttpOnly Cookie（避免 XSS 窃取）
- CSRF 防护：API Token 机制或 SameSite 策略
- 路由守卫：前端校验角色，但后端是最终权限裁决者

### 9.6 UI 质量属性
- 首屏加载时间 < 2s
- 支持响应式布局（桌面/平板）
- 文件上传支持拖拽、进度反馈
- 转换状态轮询（或 SSE/WebSocket 推送）

### 9.7 目录结构建议（如采用方式B）
ui/
├── src/ # 前端源代码
├── dist/ # 构建输出（go:embed 嵌入）
├── package.json
└── vite.config.ts

## 11. 文档维护策略

### 11.1 变更触发条件

以下情况发生时必须同步更新本文档：
- 技术选型变更（新增/替换组件）
- 部署拓扑变更
- 核心数据流变更
- 模块职责重大调整

### 11.2 变更责任与时限

| 变更类型 | 责任角色 | 完成时限 |
|----------|----------|----------|
| 架构级变更（P0） | 技术负责人 | 变更上线前完成 |
| 设计级变更（P1） | 模块负责人 | 变更上线后 3 个工作日内 |
| 实现级变更（P2/P3） | 开发者 | 代码注释同步即可，文档可延后 |

### 11.3 一致性检查

- 每季度执行一次架构文档与代码的一致性审查（由技术负责人主持）
- 审查结果记录在项目 Wiki“架构健康度”页面

### 11.4 变更记录填写规范

每次更新本文档时，必须在“文档变更记录”表格中追加一行，包含：
- 版本号（语义化版本递增）
- 变更日期（格式：YYYY-MM-DD）
- 变更内容摘要（20字以内，指向具体章节）
- 作者姓名
- 关联的 Issue 或 PR 编号（如有）
